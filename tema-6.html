Tema 06 / 07

Repositorios Git y GitHub

El último paso técnico de este curso: llevar tu proyecto a un repositorio con control de versiones y aprender a trabajar en equipo sobre el mismo código. Verás qué es Git, en qué se diferencia de GitHub, cómo profundizar en repositorios, remotos y forks, cómo organizar ramas con Gitflow, y cómo colaborar con otras personas hasta fusionar un Pull Request.

Duración estimada4 horas
NivelIntroductorio–intermedio
EntregableRepositorio propio en GitHub con Pull Request fusionado
Objetivos de aprendizaje

Qué vas a lograr en este tema

  • Explicar qué es el control de versiones y por qué es indispensable en desarrollo de software.
  • Diferenciar Git (la herramienta) de GitHub (la plataforma en la nube).
  • Distinguir repositorio local, remoto, clon y fork, y configurar colaboradores.
  • Aplicar el modelo de ramas Gitflow en un proyecto de equipo.
  • Colaborar con otras personas desarrolladoras hasta fusionar un Pull Request revisado.
Definiciones clave

Vocabulario base del tema

Control de versiones

Sistema que registra los cambios realizados sobre un conjunto de archivos a lo largo del tiempo, permitiendo volver a versiones anteriores cuando sea necesario.

Git

Sistema de control de versiones distribuido, instalado localmente, que registra el historial de cambios de un proyecto.

GitHub

Plataforma en la nube que aloja repositorios Git y añade herramientas de colaboración: issues, Pull Requests y revisión de código.

Repositorio

Carpeta de un proyecto cuyo historial de cambios es gestionado por Git. Puede ser local (en tu computador) o remoto (alojado en GitHub).

Commit

Registro puntual de un conjunto de cambios guardados en el historial del repositorio, acompañado de un mensaje descriptivo.

Rama (branch)

Línea de desarrollo independiente dentro de un repositorio, que permite trabajar en una funcionalidad sin afectar el código principal.

Pull Request (PR)

Del inglés "solicitud de incorporación de cambios": propuesta formal para fusionar los cambios de una rama a otra, abierta en GitHub para que el equipo la revise antes de aceptarla.

Gitflow

Modelo de ramas propuesto por Vincent Driessen en 2010 que organiza el trabajo en equipo en ramas con propósitos claros: main, develop, feature/*, release/* y hotfix/*.

El flujo básico de trabajo con Git

git add mueve tus cambios al área de staging; git commit los guarda como un punto del historial local; git push envía esos commits al repositorio remoto en GitHub, donde el resto del equipo puede verlos.

Repositorios en profundidad: local, remoto, clon y fork

Antes de trabajar en equipo hace falta entender bien qué tipo de repositorio se está usando en cada momento. Es la confusión más común de quien empieza con Git: no todos los repositorios "viven" en el mismo lugar ni cumplen el mismo rol.

Repositorio local

Vive en tu computador. Se crea con git init o descargando uno remoto con git clone. Ahí ocurren tus commits antes de compartirlos.

Repositorio remoto

Vive en un servidor (GitHub, GitLab, Bitbucket). Es el punto de encuentro del equipo: ahí se publican y comparten los cambios de todas las personas colaboradoras.

Clonar (clone)

Descarga una copia local completa de un repositorio remoto, incluido su historial. Se usa cuando ya tienes permiso de colaborador sobre ese repositorio.

Bifurcar (fork)

Crea tu propia copia independiente de un repositorio ajeno, dentro de tu cuenta de GitHub. Se usa para proponer cambios a proyectos donde no tienes permiso de escritura directo.

ConceptoQué esCuándo se usa

Gitflow: un modelo de ramas para trabajar en equipo

Cuando varias personas programan sobre el mismo repositorio, trabajar todas directamente sobre una única rama termina en conflictos constantes. Gitflow resuelve esto asignando un propósito fijo a cada tipo de rama.

RamaPropósitoNace deSe fusiona en
mainCódigo en producción, siempre estable y desplegable.——
developIntegración de todas las funcionalidades ya terminadas, en camino hacia la próxima versión.mainmain (vía release/*)
feature/*Una funcionalidad puntual que un solo desarrollador (o pareja) construye de forma aislada.developdevelop (vía Pull Request)
release/*Últimos ajustes antes de publicar una versión: número de versión, changelog, pruebas finales.developmain y de vuelta a develop
hotfix/*Corrección urgente de un error detectado ya en producción.mainmain y de vuelta a develop

En proyectos pequeños o de curso, muchos equipos usan una versión simplificada de Gitflow: solo main, develop y ramas feature/*, dejando release/* y hotfix/* para cuando el proyecto realmente llega a producción. El taller de este tema usa esa versión simplificada como punto de partida.

Trabajo colaborativo: de la rama al Pull Request

Un Pull Request no es solo un botón de "fusionar": es el punto donde el equipo revisa el trabajo de una persona antes de que se vuelva parte del código compartido. Es, en la práctica, la actividad de colaboración más frecuente en cualquier equipo de desarrollo real.

Publicar la rama

Con git push -u origin feature/mi-rama, la rama local queda visible en GitHub para el resto del equipo.

Abrir el Pull Request

Desde GitHub, se propone fusionar feature/mi-rama hacia develop, con una descripción clara de qué cambió y por qué.

Revisión de código

Otras personas del equipo leen el código (code review), dejan comentarios línea por línea y solicitan cambios si algo no está claro o tiene errores.

Aprobar y fusionar

Cuando el PR es aprobado ("Approve"), se fusiona a develop y la rama feature/* se elimina: ya cumplió su propósito.

Cuando dos personas modifican las mismas líneas de un archivo, aparece un conflicto de fusión: Git no puede decidir solo cuál cambio conservar y marca el archivo para que una persona lo resuelva manualmente antes de continuar. No es un error grave, es normal en el trabajo en equipo — el taller de esta página lo practica a propósito.

Taller práctico

Taller de equipo: de la idea al Pull Request con 3 desarrolladores

Este taller se resuelve en un equipo de exactamente tres personas, simulando roles reales: Dev A hace de líder técnico y crea el repositorio, Dev B y Dev C se unen como colaboradores. Construirán, sobre el Sistema de reserva de laboratorios usado en temas anteriores, tres funcionalidades en paralelo usando Gitflow simplificado, hasta fusionar un Pull Request revisado por el equipo. La guía descargable en PDF incluye el mismo recorrido con más detalle, capturas de referencia y una rúbrica de evaluación.

Equipo de 3 personas · 3–4 horas
Descargar guía completa en PDF
Paso 1

Preparación del equipo y del repositorio

Dev A crea en GitHub un repositorio privado llamado reserva-laboratorios, inicializado con README, licencia y un .gitignore. Luego agrega a Dev B y Dev C como colaboradores desde Settings → Collaborators.

Los tres instalan Git, configuran su identidad y clonan el repositorio:

git config --global user.name "Tu nombre"
git config --global user.email "tu@correo.com"
git clone https://github.com/dev-a/reserva-laboratorios.git
Paso 2

Crear la rama develop

Dev A crea la rama de integración y la publica; los otros dos la descargan.

git checkout -b develop
git push -u origin develop

Dev B y Dev C: git fetch origin seguido de git checkout develop.

Paso 3

Cada quien crea su rama feature/*

Desde develop actualizado, cada integrante crea su propia rama de trabajo:

git checkout develop
git pull origin develop
git checkout -b feature/<tu-funcionalidad>
  • Dev A → feature/formulario-reserva
  • Dev B → feature/listado-horarios
  • Dev C → feature/autenticacion-usuarios
Paso 4

Trabajo individual con commits atómicos

Cada persona construye su parte (puede ser HTML/CSS estático si aún no ven backend) y guarda avances en commits pequeños y descriptivos, no uno solo gigante al final:

git add .
git commit -m "Agrega validación de fecha en formulario de reserva"

Mientras tanto, revisan si develop tiene cambios nuevos del equipo y los integran pronto para evitar divergencias grandes:

git fetch origin
git merge origin/develop
Paso 5

Publicar la rama y abrir el Pull Request

Cuando su funcionalidad está lista para revisión, cada quien publica su rama y abre un PR hacia develop (no hacia main):

git push -u origin feature/<tu-funcionalidad>

En GitHub: botón Compare & pull request → describir qué se hizo, por qué, y cómo probarlo → asignar como revisores a los otros dos integrantes.

Paso 6

Revisión de código cruzada

Cada integrante revisa al menos un Pull Request de un compañero: lee el código, deja mínimo dos comentarios (una sugerencia y una pregunta) y decide entre Approve o Request changes. Quien recibe comentarios responde o ajusta su código y vuelve a subir cambios a la misma rama.

Paso 7

Provocar y resolver un conflicto (a propósito)

Para practicar lo inevitable: dos integrantes editan la misma línea de README.md en ramas distintas y ambos intentan fusionar a develop. Quien fusiona de segundo verá un conflicto. Se resuelve así:

git checkout develop
git pull origin develop
git merge feature/<tu-funcionalidad>
# Git marca el archivo en conflicto con <<<<<<< ======= >>>>>>>
# edita el archivo, elige qué contenido conservar, guarda
git add README.md
git commit -m "Resuelve conflicto de fusión en README"
Paso 8

Fusionar los tres Pull Requests

Con las aprobaciones del equipo, cada PR se fusiona a develop desde GitHub (botón Merge pull request) y se elimina la rama feature/* ya fusionada. Todo el equipo actualiza su copia local:

git checkout develop
git pull origin develop
Paso 9

Preparar una versión con release/*

Con las tres funcionalidades integradas en develop, Dev A crea una rama de versión, ajusta detalles finales (por ejemplo, la versión en el README) y abre el último Pull Request, esta vez hacia main:

git checkout develop
git checkout -b release/1.0.0
git push -u origin release/1.0.0
# Pull Request: release/1.0.0 → main

Al fusionar a main, se marca la versión con una etiqueta y se sincroniza de vuelta develop:

git checkout main
git pull origin main
git tag -a v1.0.0 -m "Primera versión del sistema de reserva"
git push origin v1.0.0
git checkout develop
git merge main
Paso 10

Cierre del taller

Como equipo, respondan por escrito: ¿cuántos Pull Requests abrieron?, ¿qué conflicto tuvieron que resolver y cómo?, ¿qué comentario de revisión les pareció más útil? Entreguen el enlace del repositorio con el historial de ramas y PRs visible.
